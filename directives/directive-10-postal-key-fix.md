# Directive: Fix `_postal` vs `_postal_code` Inconsistency in Initials Validator

**Severity:** MEDIUM (STRUCT-7 from synthesis)
**Audit reference:** `recon-07-admin-ui.md`; `recon-09-synthesis.md` STRUCT-7
**Target files:** `includes/ajax/class-ajax-initials.php`, possibly `includes/class-initials-validator.php`
**Estimated scope:** ~10-20 lines of changes
**Risk:** LOW-MEDIUM — fixes a feature (address-based initials sharing) that may currently be broken for some clients
**Must complete before:** v1.1 release

---

## Context

The plugin has a vocabulary inconsistency around postal code key names:

| Place | Key used | Form/DB |
|---|---|---|
| `MealsDB_Client_Form::$db_columns` (form-side whitelist) | `address_postal`, `delivery_address_postal` | Form |
| `MealsDB_Ajax_Initials::get_client_data_from_request` | `address_postal_code`, `delivery_address_postal_code` | Mixed |
| `MealsDB_Initials_Validator::normalize_delivery_address` | Accepts BOTH `delivery_address_postal_code` AND `delivery_postal_code` | Mixed |

When the user submits the address-based initials validation AJAX, the form sends `address_postal` (per the form's `$db_columns` vocabulary). The AJAX handler `get_client_data_from_request` looks for `address_postal_code`. **The postal field is silently dropped from the address data**, leaving it empty.

The validator's `is_address_empty` then sees the postal as missing and treats the address as incomplete, **silently disabling address-based initials sharing**. Operators see "duplicate initials" rejected on shared-address pairs where sharing should be allowed.

There's a historical bug fix already in the code (per audit, in `class-initials-validator.php`) that fixed a similar `postal` vs `postal_code` mismatch in the normalized array. This is a related but distinct instance.

## Pre-flight verification

### Step P1: Confirm the form sends `address_postal`

```bash
grep -n "address_postal\|delivery_address_postal" includes/class-admin-ui.php views/ assets/js/ --include="*.php" --include="*.js" 2>/dev/null | head -20
```

Look at the form rendering and the JS that handles the validate-initials AJAX call.

Likely findings:
- The form input `name="address_postal"` is generated by `render_client_form`.
- The JS at `assets/js/client-initials.js` (or similar) reads form values and POSTs to the AJAX endpoint with the same key name.

If you find the JS uses `address_postal_code` (matching the AJAX handler's expectation), the inconsistency is on the JS side. If it uses `address_postal` (matching the form), the inconsistency is on the AJAX handler side. Document both possibilities.

### Step P2: Confirm the AJAX handler expects `_postal_code`

```bash
grep -n "address_postal\|delivery_address_postal" includes/ajax/class-ajax-initials.php
```

Locate `get_client_data_from_request`. Read the full method. Document which field names it reads from `$_POST`.

### Step P3: Trace through the validator

```bash
grep -n "postal\|delivery_address" includes/class-initials-validator.php
```

Find `normalize_delivery_address` and `is_address_empty`. Document:
- Which keys `normalize_delivery_address` accepts as input (it may accept multiple variants per the audit).
- Which key `is_address_empty` checks.

If the validator's `normalize_delivery_address` accepts BOTH `address_postal` and `address_postal_code` (and normalizes to a single internal key like `postal`), then fixing the AJAX handler to use `address_postal` is sufficient — the validator will handle it.

If the validator only accepts ONE form, fix in BOTH places (AJAX handler AND validator) to use the canonical form.

---

## The decision

There are two competing canonical names: `address_postal` (matches the form's `$db_columns`) and `address_postal_code` (more explicit, matches WP standards for postal codes in addresses).

**Recommendation:** standardize on `address_postal` because:
1. It matches the form-side vocabulary already declared in `MealsDB_Client_Form::$db_columns`.
2. The form's POST values use this name, so the AJAX handler is the one that's misaligned.
3. Changing the form would break the form-side vocabulary in `$db_columns` and risk a cascade of other bugs.

If the dev wants `address_postal_code` instead, that's also valid but would require changing the form's `$db_columns`, the `map_form_to_db` mapping, possibly the column name on `meals_clients` (currently `postal_code`), and the JS. **Significantly larger scope.** Confirm with the dev before going that route.

**This directive proceeds with `address_postal` as canonical.**

## The fix

### Step F1: Update the AJAX handler to read `_postal`

In `includes/ajax/class-ajax-initials.php`, locate `get_client_data_from_request`. The method reads address fields from `$_POST`. Change the postal-code-related keys:

Before:
```php
private static function get_client_data_from_request(): array {
    return [
        'address_street_number'  => sanitize_text_field(wp_unslash($_POST['address_street_number'] ?? '')),
        'address_street_name'    => sanitize_text_field(wp_unslash($_POST['address_street_name'] ?? '')),
        'address_unit'           => sanitize_text_field(wp_unslash($_POST['address_unit'] ?? '')),
        'address_city'           => sanitize_text_field(wp_unslash($_POST['address_city'] ?? '')),
        'address_postal_code'    => sanitize_text_field(wp_unslash($_POST['address_postal_code'] ?? '')),
        'delivery_address_street_number'  => sanitize_text_field(wp_unslash($_POST['delivery_address_street_number'] ?? '')),
        'delivery_address_street_name'    => sanitize_text_field(wp_unslash($_POST['delivery_address_street_name'] ?? '')),
        'delivery_address_unit'           => sanitize_text_field(wp_unslash($_POST['delivery_address_unit'] ?? '')),
        'delivery_address_city'           => sanitize_text_field(wp_unslash($_POST['delivery_address_city'] ?? '')),
        'delivery_address_postal_code'    => sanitize_text_field(wp_unslash($_POST['delivery_address_postal_code'] ?? '')),
    ];
}
```

After:
```php
private static function get_client_data_from_request(): array {
    // The form posts the postal field as 'address_postal' / 'delivery_address_postal'
    // per MealsDB_Client_Form::$db_columns. A previous version of this handler
    // read 'address_postal_code' which the form never sent — the postal was
    // silently empty in the validator's address comparison, silently
    // disabling address-based initials sharing.
    //
    // The returned array uses the form-side vocabulary. The validator
    // (normalize_delivery_address) accepts this and normalizes internally.
    return [
        'address_street_number'  => sanitize_text_field(wp_unslash($_POST['address_street_number'] ?? '')),
        'address_street_name'    => sanitize_text_field(wp_unslash($_POST['address_street_name'] ?? '')),
        'address_unit'           => sanitize_text_field(wp_unslash($_POST['address_unit'] ?? '')),
        'address_city'           => sanitize_text_field(wp_unslash($_POST['address_city'] ?? '')),
        'address_postal'         => sanitize_text_field(wp_unslash($_POST['address_postal'] ?? '')),
        'delivery_address_street_number'  => sanitize_text_field(wp_unslash($_POST['delivery_address_street_number'] ?? '')),
        'delivery_address_street_name'    => sanitize_text_field(wp_unslash($_POST['delivery_address_street_name'] ?? '')),
        'delivery_address_unit'           => sanitize_text_field(wp_unslash($_POST['delivery_address_unit'] ?? '')),
        'delivery_address_city'           => sanitize_text_field(wp_unslash($_POST['delivery_address_city'] ?? '')),
        'delivery_address_postal'         => sanitize_text_field(wp_unslash($_POST['delivery_address_postal'] ?? '')),
    ];
}
```

### Step F2: Update the validator to accept `_postal`

In `includes/class-initials-validator.php`, locate `normalize_delivery_address`. It should accept the form-side key name. Per the audit, the validator already accepts BOTH form-side names (`delivery_address_street_name`) AND DB-side names (`delivery_street_name`). Verify the same flexibility exists for postal.

If `normalize_delivery_address` already accepts both `address_postal` and `address_postal_code`:
- No change needed in the validator.

If it only accepts `_postal_code`:
- Add `_postal` as an accepted alias.

Example:

Before (illustrative):
```php
public static function normalize_delivery_address(array $data): array {
    $postal = (string) ($data['delivery_address_postal_code']
                     ?? $data['delivery_postal_code']
                     ?? '');
    // ...
}
```

After:
```php
public static function normalize_delivery_address(array $data): array {
    // Accept multiple key names because callers use different vocabularies:
    //   - 'delivery_address_postal' (form-side, from MealsDB_Client_Form::$db_columns)
    //   - 'delivery_address_postal_code' (legacy/AJAX older form)
    //   - 'delivery_postal_code' (DB-side raw column name)
    // The validator should not care which the caller used.
    $postal = (string) (
        $data['delivery_address_postal']
        ?? $data['delivery_address_postal_code']
        ?? $data['delivery_postal_code']
        ?? ''
    );
    // ...
}
```

Apply the same multi-accept pattern to billing address postal:
```php
$billing_postal = (string) (
    $data['address_postal']
    ?? $data['address_postal_code']
    ?? $data['postal_code']
    ?? ''
);
```

### Step F3: Verify the JS sends the form-side key

Open `assets/js/client-initials.js` (or wherever the validate-initials AJAX call originates). Confirm it reads form values by the form-side key name:

```bash
grep -n "address_postal\|delivery_address_postal" assets/js/ -r
```

Likely the JS reads `$('input[name="address_postal"]').val()`. If it reads `$('input[name="address_postal_code"]').val()`, that's another instance of the same bug — the JS would always read empty. Fix to match the form's actual input name.

**Do not change the JS in this directive without confirming.** If you find a discrepancy, document it and ask the dev. JS changes have a separate test path (browser-side).

## Testing

### Step T1: Static check

```bash
php -l includes/ajax/class-ajax-initials.php
php -l includes/class-initials-validator.php
```

### Step T2: Functional test — verify address-sharing works

> **Manual test required:**
> 1. On staging, identify a client at a known address (e.g. "123 Main St, Moncton, E1C 1A1") with delivery initials "ABC".
> 2. Navigate to Meals DB → Add New Client.
> 3. Enter a new client with the SAME billing address ("123 Main St, Moncton, E1C 1A1") but different name (e.g. "Jane Smith").
> 4. Tab through the form. Type "ABC" into the delivery initials field.
> 5. Click "Validate Initials" (or trigger the AJAX validation).
> 6. Expected: validator returns `{valid: true, shared: true, sharing_with: '<existing client name>'}`. UI shows "These initials are shared with [other client at same address]" — allowed.
>
> Repeat with a DIFFERENT address ("456 Pine St, Moncton, E1A 1A1"):
> 7. Validator should return `{valid: false}` because the initials are taken at a different address. UI shows "These initials are already in use." — rejected.

### Step T3: Regression test

Verify the basic non-sharing case still works:
1. Try to validate "XYZ" (unique initials) at a new address.
2. Expected: `{valid: true, shared: false}`.

### Step T4: Verify the previous broken behavior is fixed

Check the audit log: `MealsDB_Logger::get_recent_logs` or query `meals_audit_log` for past "initials validation rejected at shared address" patterns. If those exist historically, this fix should reduce them.

## Out of scope for this directive

- Do NOT rename the actual DB column `postal_code` (the DB-side name on `meals_clients`). That's an architectural change requiring a migration.
- Do NOT change the form's input name from `address_postal` to anything else. That cascades into `$db_columns` and other consumers.
- Do NOT modify other AJAX handlers' address-handling code unless they have the same exact bug. Each handler needs separate analysis.
